# 产品经理工作流方法论

## 核心理念

产品经理的工作流不应该是线性的，而应该是**螺旋上升**的：理解需求 → 提出假设 → 设计方案 → 验证 → 修正假设 → 继续迭代。

在面对模糊需求时，最重要的能力不是"想清楚再动手"，而是"用产出推动思考"。一个粗糙的 v0.1 比一个完美的想法更有价值。

## 工作流阶段

### 阶段 1：需求理解

**核心任务**：把模糊的用户描述翻译成产品语言。

- 复述需求：确认你和用户说的是同一件事
- 挖掘本质：用户说的不一定是用户需要的，找到真正的痛点
- 定位目标：这个需求为谁解决什么问题，带来什么价值
- 划定边界：初步判断做什么、不做什么

**关键原则**：不要停留在用户说的表面需求，要追问 WHY。

### 阶段 2：需求澄清

**核心任务**：用关键问题快速对齐方向。

- 聚焦在用户、场景、价值、范围、优先级
- 不超过 8 个问题
- 给选项而不是开放式提问
- 即使得不到回答，也要基于假设推进

**关键原则**：澄清问题是用来对齐的，不是用来阻断的。

### 阶段 3：产品假设

**核心任务**：把不确定的信息转化为明确的假设。

- 每个假设都要写清楚，让用户可以直接确认或修改
- 假设覆盖：用户、业务、场景、功能、设计
- 假设是对齐的工具，不是最终答案

**关键原则**：假设是快速推进的手段。确认假设比推倒重来成本低得多。

### 阶段 4：用户场景与流程

**核心任务**：把需求转化为具体的人和具体的行为。

- 用户角色要具体，不要用"普通用户"这种模糊描述
- 使用路径要完整，从触发到结束
- 业务流程图可以帮助发现遗漏的节点
- 状态流转要覆盖正常和异常

**关键原则**：如果画不出流程图，说明你对需求的理解还不够。

### 阶段 5：PRD 撰写

**核心任务**：用结构化的方式把需求写清楚。

- 13 个模块覆盖需求的全部维度
- "不做什么"和"做什么"一样重要
- 异常情况要穷举，避免上线后踩坑
- 验收标准要可测试，不能模糊

**关键原则**：PRD 是团队协作的契约，不是文学创作。

### 阶段 6：信息架构设计

**核心任务**：把功能转化为页面和导航。

- 页面清单要完整，不漏页面
- 页面跳转关系要清晰
- 每个页面要有明确的核心目的
- 页面优先级帮助规划迭代

**关键原则**：用户用的时候不应该思考"这个在哪里"。

### 阶段 7：页面设计说明

**核心任务**：为每个页面提供完整的设计规格。

- 不只是界面长什么样，而是页面要完成什么任务
- 状态设计要覆盖：默认、空、加载、异常
- 交互说明要具体到手势和反馈
- 组件要复用，保持一致性

**关键原则**：页面设计的质量 = 所有状态都考虑到了 / 只有默认态。

### 阶段 8：原型生成

**核心任务**：把设计转化为可交互的原型，快速验证。

- 提示词要包含完整的上下文（背景、风格、交互）
- 要求产出有基础交互，不只是静态图
- 移动端优先，因为大部分产品先做移动端

**关键原则**：一个可交互的原型胜过 100 页 PRD。

## 工作流使用姿势

1. **不要跳过步骤**：每一步都在为下一步打基础
2. **每步都要输出**：输出的目的是让用户确认，不是自嗨
3. **假设要显式**：让用户知道哪些是确定的，哪些是你假设的
4. **持续迭代**：v0.1 → v0.2 → v1.0，不追求一步到位
