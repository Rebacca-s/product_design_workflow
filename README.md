# 产品设计工作流 — AI 产品设计总导演

从模糊需求到研发交付物的完整产品设计工作流引擎。

## 核心理念

不是只生成单个 PRD，也不是固定 12 章节。而是从模糊需求开始，**先识别需求类型，再动态装配交付物和 PRD 章节**。

最终交付给研发的是 **PRD 主文档 + 原型说明 + 必要的专项文档引用路径**。

## 适用场景

- 接到一个模糊的产品需求，不知道从哪里开始
- 需要快速产出一套完整的研发交付物
- 需要为移动端 App / 小程序 / 后台管理系统设计页面
- 需要给设计师或 AI 原型工具输出清晰的页面设计说明
- 需要给 Cursor / Claude 生成可交互的 HTML 原型
- 希望长期沉淀自己的产品方法论和案例

## 使用方式

### 启动产品设计工作流

```text
/product-start 你的需求描述
```

例如：

```text
/product-start 做一个 AI 会议纪要总结小程序
/product-start 分销记录列表加搜索
/product-start 后台新增活动订单状态管理
```

### 工作流 7 步骤

| Step | 名称 | 产出 |
|------|------|------|
| 1 | 接收需求 + 识别需求类型 | 需求拆解 + 类型识别（对话输出） |
| 2 | 生成交付物与章节规划 | `00_交付物与章节规划.md` |
| 3 | 按规划生成非 PRD 交付物 | BRD、需求分析（如启用） |
| 4 | 动态装配 PRD | `03_PRD_产品需求文档.md`（仅生成启用章节） |
| 5 | 判断章节外拆 | `04_PRD_专项文档/`（按需） |
| 6 | 生成原型相关交付物 | 原型说明 + HTML 提示词（如启用） |
| 7 | 生成研发交付检查清单 | `07_研发交付检查清单.md` |

### 启动前端实现工作流

```text
/frontend-implement outputs/需求名称 local_projects/frontend/项目名称
```

例如：

```text
/frontend-implement outputs/哆爱宠分销记录搜索 local_projects/frontend/duoai_pet_frontend
```

### 双 Skill 架构

```text
模糊需求
  ↓
/product-start          ← 产品需求设计（不改代码）
  ↓
产品交付物（PRD + 原型说明 + 检查清单）
  ↓
/frontend-implement    ← 前端代码实现（基于交付物改代码）
  ↓
前端代码修改
```

| Skill | 职责 | 修改代码 |
|-------|------|----------|
| `/product-start` | 需求分析、PRD 生成、原型说明、检查清单 | 不修改 |
| `/frontend-implement` | 基于已确认的交付物修改前端代码 | 负责 |

> `/product-start` 可以读取 `context/products/` 和 `local_projects/frontend/` 用于理解业务现状，但默认不修改代码。代码修改由 `/frontend-implement` 负责。 |

## 模板三层分层

`templates/` 下分成三类，各司其职：

| 目录 | 定位 | 核心作用 | 示例 |
|------|------|----------|------|
| `deliverables/` | 交付物级模板 | 规定一整份交付文档的整体结构 | `AIGC_BRD_8章节交付物模板.md`、`PRD主文档骨架模板.md`、`原型说明_交付物模板.md` |
| `presets/` | PRD 预设方案 | 根据需求类型推荐章节组合、交付物范围、写作深度、外拆方向 | `AI功能模板_PRD预设.md` |
| `sections/` | 章节级模板 | 规定某个 PRD 章节的写法 | `页面与交互说明_章节模板.md` |

### 关键文件的定位

**PRD主文档骨架模板** — 它是"文档壳子"，不是章节选择规则。它只规定 PRD 主文档的基础外壳：
- 封面信息
- 更新记录
- 文档说明
- 本次交付物路径
- 本次启用章节目录
- 章节正文占位
- 专项文档引用
- 待确认事项
- 验收标准入口

**PRD 预设（presets/）** — 它们是"章节组合建议"，不是最终 PRD，也不是强制模板。只负责根据不同需求类型推荐：
- 推荐交付物
- 推荐章节组合
- 推荐写作深度
- 推荐外拆方向

**章节模板（sections/）** — 它们是"章节写法"，说明某一个章节怎么写：
- `页面与交互说明_章节模板.md`
- `模型选型_章节模板.md`
- `Prompt工程_章节模板.md`
- `验收标准_章节模板.md`

**原型说明_交付物模板** — 它是"完整交付物"，对应最终输出的 `05_原型说明文档.md`，用来规定：
- 页面清单
- 页面跳转关系
- 页面信息架构
- 核心页面说明
- 全局交互规则
- 页面状态
- 权限状态
- 异常状态

**页面与交互说明_章节模板** — 它是"其中一个章节"，不是完整交付物。它是 PRD 主文档或原型说明文档中的一个章节模板，用来说明某个页面或某个模块的：
- 页面目标
- 页面结构
- 信息层级
- 组件说明
- 字段展示
- 按钮操作
- 默认状态
- 空状态
- 加载状态
- 异常状态
- 交互规则

> 一句话：**PRD主文档骨架模板是"文档壳子"；PRD预设是"章节组合建议"；sections 是"章节写法"；原型说明是"完整交付物"；页面与交互说明是"其中一个章节"。**

## PRD 章节库（25 章，按需装配）

| 分类 | 章节 ID | 章节名称 |
|------|---------|----------|
| **A. 通用基础** | A1-A9 | 需求背景、需求目标、用户角色与场景、功能范围、功能说明、页面与交互、字段与规则、异常情况、验收标准 |
| **B. 条件启用** | B1-B6 | 业务流程图、系统流程图、状态流转、权限设计、埋点设计、风险与依赖 |
| **C. AI 专属** | C1-C10 | AI 必要性、模型选型、AI 节点设计、Prompt 工程、AI 异常兜底、效果保障、AI 能力边界、评测体系、数据飞轮、Bad Case 回流 |

## 三种典型装配

| 需求 | 示例 | 启用交付物 | 启用章节 |
|------|------|-----------|---------|
| AI 新产品 | "AI 纪要总结小程序" | 00+01+02+03+04+05+06+07 | A1-A9 + B1/B2/B5 + C1-C10 |
| 非 AI 小迭代 | "分销列表加搜索" | 00+02(简化)+03+07 | A1-A9(简化) |
| 后台+状态流转 | "活动订单状态管理" | 00+01+02+03+05+07 | A1-A9 + B3/B4 |

## 核心设计原则

1. **先规划再生成**：00_规划文档每次必须先生成
2. **按需装配**：章节不固定，根据需求类型动态启用/禁用
3. **非 AI 不生成 AI 章节**：不写"不适用"占位
4. **PRD 是总装文档**：复杂内容外拆为专项文档
5. **10 条外拆条件**：满足任意一条即外拆
6. **信息不足写"待确认"**：不编造
7. **所有交付物可独立阅读**：不给研发碎片

## context/products/ 与 local_projects/frontend/ 的区别

| 目录 | 是否提交 | 作用 |
|------|----------|------|
| `context/products/` | 提交 | 沉淀业务背景、页面地图、角色权限、流程、字段、接口说明 |
| `local_projects/frontend/` | 不提交 | 放真实前端源码，让 Claude Code 读取和修改代码 |

- `context/products/` 是手工维护的产品现状文档
- `local_projects/frontend/` 是真实前端项目的本地工作副本
- 真实前端项目通过 `.gitignore` 排除，不提交到 product_design_workflow 仓库
