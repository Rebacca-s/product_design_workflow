# 产品设计工作流 — AI 产品设计总导演（v4.1 增强版）

从模糊需求到研发交付物的完整产品设计工作流引擎。

## 四层架构

```text
用户输入
    ↓
Master Agent          ← 统一入口：识别意图 → 分类 → 路由 → 编排
    ↓
Capability Registry   ← 能力映射中枢
    ↓
Domain Agent          ← Product / Review / Frontend / General
    ↓
Skill                 ← product-start / prd-review / frontend-implement
    ↓
规则、模板、上下文和交付物
```

## 核心理念

不是只生成单个 PRD，也不是固定 12 章节。而是从模糊需求开始，**先识别需求类型，再动态装配交付物和 PRD 章节**。

**v4.1 核心升级**：
- **需求信息分类**：用户输入自动拆分为业务事实、明确需求、运营策略、案例、假设、AI推导、待澄清事项
- **案例与规则强制分离**：用户举的例子不自动成为产品通用规则，运营策略不默认固化为系统功能
- **需求抽象**：从具体案例中提取通用产品能力
- **关键需求澄清**：AI 自主判断低风险细节，只对影响方向的关键问题提问，最多两轮
- **业务逻辑深度核验**：Review Agent 新增角色权责、数据归属、流程闭环、页面归属、案例污染检查（现共 18 个维度）

## 适用场景

- 接到一个模糊的产品需求，不知道从哪里开始
- 需要快速产出一套完整的研发交付物
- 需要为移动端 App / 小程序 / 后台管理系统设计页面
- 需要给设计师或 AI 原型工具输出清晰的页面设计说明
- 需要给 Cursor / Claude 生成可交互的 HTML 原型
- 需要系统化评审 PRD 质量
- 希望长期沉淀自己的产品方法论和案例

## 使用方式

### 直接说你要做什么（推荐）

不需要输入任何 Skill 名称，直接描述你的需求：

```text
做一个 AI 会议纪要总结小程序
分销记录列表加搜索
后台新增活动订单状态管理
这个门店管理页面需要增加门店类型字段
帮我看看这份需求有没有逻辑问题
根据确认的 PRD 修改前端页面
```

Master Agent 会自动识别意图并路由到对应的 Agent 和 Skill。

### 也可以显式调用 Skill

```text
/product-start 你的需求描述
/prd-review outputs/需求名称
/frontend-implement outputs/需求名称 local_projects/frontend/项目名称
```

## 能力矩阵

| 你说的 | 自动路由到 | 做什么 |
|--------|-----------|--------|
| "设计一个..."、"这个页面加..."、"规则改一下" | Product Agent → product-start | 产品需求设计 |
| "检查一下"、"有没有问题"、"是否完整" | Review Agent → prd-review | PRD 评审 |
| "改前端"、"实现页面"、"修改代码" | Frontend Agent → frontend-implement | 前端代码实现 |
| "什么是..."、"解释一下" | General Agent | 通用问答 |

## 工作流

### product-start（产品需求设计，v4.1 增强版）

| 阶段 | 名称 | 产出 |
|------|------|------|
| 0 | 上下文读取 | 产品上下文 + 前端项目理解 |
| 1 | 需求理解与信息分类 | 信息分类（业务事实/需求/运营策略/案例/假设/AI推导/待澄清） |
| 2 | 需求抽象 | 通用产品能力 + 案例与规则分离 |
| 3 | 关键需求澄清 | 必须确认的问题 + 按假设继续的事项 |
| 4 | 需求类型与影响范围识别 | 需求类型 + 影响范围 |
| 5 | 交付物与章节规划 | `00_交付物与章节规划.md` |
| 6 | 需求分析 | `02_需求分析与范围定义.md` |
| 7 | PRD 生成或修改 | `03_PRD_产品需求文档.md` |
| 8 | 专项文档 | `04_PRD_专项文档/` |
| 9 | 原型说明 + HTML提示词 | `05_原型说明文档.md` + `06_HTML原型生成提示词.md` |
| 10 | 研发交付检查 + Review 评审 | `07_研发交付检查清单.md` + 评审报告 |

> **核心规则**：需求未经过第 1-3 阶段（信息分类、抽象、澄清），不得直接进入第 5 阶段（交付物规划）。

### prd-review（评审工作流，v4.2 双模式版）

| 模式 | 名称 | 适用场景 | 读取范围 | 输出 |
|------|------|----------|----------|------|
| A | PRD 文档评审 | 评审 PRD 质量、检查需求完整性 | PRD + 专项文档 + 原型说明 | 18 维度报告 |
| B | 已有方案评审（v4.2 新增） | 优化方案、评审页面、排查流程、找业务漏洞 | PRD + 原型说明 + HTML原型 + 前端代码 + 业务上下文 | 5 维报告（业务逻辑/产品设计/页面交互/数据流程/修改优先级） |

> **核心规则**：两种模式均不得直接修改文件。必须等用户确认后，再由 Master Agent 路由到对应 Agent 执行。

### frontend-implement（前端代码实现，v4.1 增强版，17 阶段）

| 阶段 | 名称 | 核心能力 |
|------|------|----------|
| 0 | 任务路由与模式识别 | 区分全新页面/增量修改/原型演示/正式实现 |
| 1-2 | 读取需求与项目 | 需求理解 + 项目结构分析 |
| 3 | 分析现有代码与设计规范 | 找同类页面/组件作为参照 |
| 4 | 业务流程与页面映射 | 先梳理数据流转，再规划页面 |
| 5 | 建立页面设计计划 | `08_前端页面实施与进度计划.md`（跨轮维护） |
| 6 | 数据来源与 Mock 策略 | 真实接口优先，Mock 隔离 |
| 7 | 多状态模拟方案 | 状态清单 + 演示切换入口 |
| 8 | 代码修改计划 | 含原功能保护清单（需确认） |
| 9-11 | 逐页实施+交互闭环+状态演示 | 样式继承、P0/P1/P2 交互优先级 |
| 12-15 | 一致性+流程+回归检查 | 样式一致性、PRD一致性、流程完整性、原功能回归 |
| 16 | 更新计划+输出结果 | 进度更新 + 实现总结 |

> **核心规则**：不得在没有页面计划的情况下直接编码。Mock 数据不覆盖真实接口。发现业务需求变更必须返回 Product Agent。

## 核心设计原则

1. **强制路由**：所有用户输入先经过 Master Agent 分类和路由
2. **先规划再生成**：00_规划文档每次必须先生成
3. **按需装配**：章节不固定，根据需求类型动态启用/禁用
4. **非 AI 不生成 AI 章节**：不写"不适用"占位
5. **PRD 是总装文档**：复杂内容外拆为专项文档
6. **信息不足写"待确认"**：不编造
7. **所有交付物可独立阅读**：不给研发碎片
8. **每次回复透明告知工具调用**：见 `rules/工具调用透明规则.md`
9. **每个阶段输出状态卡**：见 `rules/阶段状态提示规则.md`
10. **用户无需输入 Skill 名称**：Master Agent 自动识别和路由

## 禁止绕过

| 禁止行为 | 说明 |
|----------|------|
| 未分类直接修改 | 必须先路由，再执行 |
| 跳过 Agent 直接改 PRD | 产品需求必须经过 Product Agent |
| 跳过 Agent 直接改代码 | 前端修改必须经过 Frontend Agent |
| 评审不经过 Review Agent | 检查/审核必须经过 prd-review |
| 因无 Skill 名就跳过 | 路由自动完成，不依赖用户显式输入 |
