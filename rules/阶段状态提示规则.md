# 阶段状态提示规则

## 核心原则

执行任何 Skill 时，必须在对话中持续告知用户当前进展。不在最后才总结，而是每个阶段开始时提示、阶段中持续更新、完成后输出总览。

---

## 一、适用范围

适用于所有核心 Skill：

- `/product-start`
- `/frontend-implement`
- 后续新增的其他 Skill

---

## 二、阶段状态卡格式

每进入一个新阶段时，必须先输出：

```markdown
## 当前阶段：第 X 阶段 — 阶段名称

| 项目 | 内容 |
|------|------|
| 当前阶段 | 第 X 阶段：阶段名称 |
| 正在处理 | 当前正在做什么 |
| 本阶段产出 | 本阶段会生成什么 |
| 下一阶段 | 下一步会进入什么 |
| 是否需要我确认 | 是 / 否 |
```

**规则**：

- 如果"是否需要我确认"为"否"，继续推进，不要停下来
- 如果"是否需要我确认"为"是"，明确告知用户需要确认什么
- "视情况"时说明什么情况下需要确认

---

## 三、阶段切换规则

当工作流从一个阶段进入另一个阶段时，必须重新输出阶段状态卡。

不要只在开始时输出一次。

---

## 四、阶段中进展提示

如果某个阶段执行时间较长，必须在阶段内持续提示进展：

```markdown
### 阶段进展

当前仍在第 X 阶段：阶段名称。

已完成：
- [已完成的子任务1]
- [已完成的子任务2]

正在处理：
- [正在处理的子任务]

下一步：
- [下一步子任务]
```

## 五、/product-start 阶段定义

执行 `/product-start` 时，按以下阶段提示：

| 阶段 | 名称 | 产出 | 通常是否需要确认 |
|------|------|------|-----------------|
| 第 0 阶段 | 上下文读取 | 产品上下文理解 + 前端项目结构扫描 | 否 |
| 第 1 阶段 | 需求类型识别 | 需求拆解 + 类型识别结果 | 否（除非 > 3 个维度不确定） |
| 第 2 阶段 | 交付物与章节规划 | `00_交付物与章节规划.md` | 视情况（有不确定的启用/不启用时需确认） |
| 第 3 阶段 | 需求分析与范围定义 | `02_需求分析与范围定义.md`（如启用） | 否（假设已标注） |
| 第 4 阶段 | PRD 主文档生成 | `03_PRD_产品需求文档.md` | 否（假设已标注） |
| 第 5 阶段 | 专项文档判断与生成 | `04_PRD_专项文档/`（如启用） | 否 |
| 第 6 阶段 | 原型说明生成 | `05_原型说明文档.md`（如启用） | 否 |
| 第 7 阶段 | HTML 原型提示词生成 | `06_HTML原型生成提示词.md`（如启用） | 否 |
| 第 8 阶段 | 研发交付检查 | `07_研发交付检查清单.md` | 否 |

## 七、进度提示时机

必须在以下时机输出阶段状态：

1. 开始执行 Skill 时（进入第 0 阶段）
2. 每次从一个阶段进入另一个阶段时
3. 阶段执行时间较长时（阶段内进展提示）
4. 需要用户确认时
5. 完成所有阶段时（工作流完成总览）

---

## 八、工作流完成总览

全部阶段完成后，必须输出：

```markdown
## 工作流完成总览

| 项目 | 内容 |
|------|------|
| 已完成阶段 | 第 0 阶段 ~ 第 X 阶段 |
| 生成交付物 | [文件列表] |
| 未生成交付物 | [文件列表] + [原因] |
| 待确认事项 | [列表] |
| 下一步建议 | [如：确认后可使用 /frontend-implement 进行前端实现] |
```

---

## 九、注意事项

1. **不要只在最后总结**：在阶段切换时就要输出，让用户随时知道进度
2. **阶段状态卡必须简洁**：一个表格 + 一行说明，不要写成长文
3. **确认时机必须准确**：只有涉及方案选择、范围决策时才需要确认，其他时候主动推进
4. **阶段内进度不啰嗦**：PRD 生成过程中每完成一个大章节可以在对话中提一句，但不用每个小标题都提示
5. **最终总览必须输出**：无论工作流长短，完成后必须输出总览
