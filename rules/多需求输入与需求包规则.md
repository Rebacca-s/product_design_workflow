# 多需求输入与需求包规则

## 核心原则

当用户一次输入多个需求时，不逐个生成 PRD（文档太多），也不全部塞进一个 PRD（文档太大），而是先进行需求归组，将相关需求合并为需求包，再按需求包生成交付物。

---

## 一、需求包概念

需求包不是单个小需求，也不是整个版本。

需求包是一次研发交付中相对独立、适合一起理解、一起评审、一起开发、一起验收的一组需求。

一个需求包可以包含多个需求项。

需求包内部的需求应该彼此相关；不同需求包之间应该尽量相互独立。

一个需求包完成或延期，不应该严重影响另一个需求包的开发和验收。

---

## 二、版本文件夹规则

### 触发条件

满足以下任一条件时，创建版本文件夹：

1. 一次输入多个需求（需生成多个需求包）
2. 用户明确说这是某个版本 / 某次迭代 / 某批需求

### 命名格式

```
outputs/V版本号_日期_版本主题/
```

- 如果用户提供了版本号，使用用户提供的版本号
- 如果用户没有提供版本号，使用 `版本_YYYY-MM-DD_主题`
- 如果用户没有提供主题，根据需求内容总结一个简短主题（不超过 15 个字）

### 示例

```
outputs/
└── V1.3.0_2026-06-28_分销与活动优化/
    ├── 需求包01_分销页面优化/
    ├── 需求包02_活动订单管理优化/
    └── 需求包03_Banner跳转优化/
```

### 重要约束

1. 版本文件夹只是分类容器，不是交付物
2. **不要生成 `版本总览.md`**
3. **不要生成 `版本PRD主文档.md`**
4. 每个需求包内部仍按 `rules/交付物启用规则.md` 生成文档
5. 如果某个需求包很小，可以简化交付物，但必须至少有：

```
00_交付物与章节规划.md
03_PRD_产品需求文档.md
07_研发交付检查清单.md
```

---

## 三、需求归组规则

当一次输入多个需求时，先识别所有需求项，再按以下规则判断合并或拆分。

### 适合合并为同一需求包的情况

满足以下任意多个条件时，可以合并：

1. 属于同一个业务目标
2. 属于同一个产品模块
3. 属于同一个页面或页面组
4. 属于同一个用户角色或同一个端口
5. 属于同一条操作链路
6. 涉及同一批字段、状态、筛选、搜索、列表展示
7. 需要同一个研发一起开发
8. 可以一起评审、一起验收
9. 拆开后会导致上下文断裂
10. 拆开后研发需要在多个 PRD 之间来回看

### 应该拆成不同需求包的情况

满足以下任意条件时，应该拆分：

1. 业务目标明显不同
2. 所属模块明显不同
3. 面向用户角色明显不同
4. 所属端口不同且开发链路不同
5. 上线节奏可以独立
6. 一个需求完成与否不影响另一个需求
7. 一个需求是完整大功能，另一个只是小优化
8. 一个需求涉及 AI、模型、Prompt、评测，另一个是普通非 AI 功能
9. 一个需求涉及支付、订单、权限、状态机等高风险内容，另一个只是普通页面调整
10. 放在一起会导致 PRD 过长或评审范围过大

---

## 四、不要过度切分规则

不要把需求切分得过细。

以下情况**不要拆成多个需求包**：

1. 同一个页面里的搜索、筛选、字段展示、空状态、按钮操作
2. 同一个列表的字段、筛选、排序、导出
3. 同一个表单的字段、校验、提交、成功提示
4. 同一个订单流程的状态、操作、异常、通知
5. 同一个活动报名链路的列表、详情、报名、支付、订单
6. 同一个 AI 生成链路的输入、生成、结果展示、重新生成、保存

这些应该作为同一个需求包中的多个需求项。

---

## 五、需求包内 PRD 写法

一个需求包可以包含多个需求项。PRD 主文档中需要先写出本需求包包含的所有需求项。

### 需求项清单格式

```markdown
## 本需求包包含的需求项

| 需求项编号 | 需求项名称 | 优先级 | 所属模块 | 是否独立验收 |
|---|---|---|---|---|
| R1 | 分销记录增加用户搜索 | P0 | 分销记录列表 | 是 |
| R2 | 分销记录展示用户头像和昵称 | P0 | 分销记录列表 | 是 |
| R3 | 团队人数列表展示用户电话 | P1 | 团队人数列表 | 是 |
```

### 规则

1. 一个需求包内可以有多个需求项
2. 每个需求项要能独立验收
3. 这些需求项共享同一个 PRD 上下文
4. 如果某个需求项延期，不应影响同需求包内其他已完成需求项验收，除非它们存在明确依赖
5. PRD 中要写明需求项之间是否存在依赖

### 需求项依赖声明格式

```markdown
## 需求项依赖关系

| 需求项 | 依赖项 | 依赖说明 |
|--------|--------|----------|
| R2 | R1 | 搜索功能是展示头像和昵称的前提 |
| R3 | 无 | 独立 |
```

---

## 六、需求包大小控制规则

一个需求包不宜过大。

### 需要继续拆分的信号

如果一个需求包满足以下情况，需要考虑继续拆分：

1. 包含超过 8 个需求项
2. 涉及超过 3 个一级模块
3. 涉及超过 3 类用户角色
4. 涉及超过 2 条完整业务链路
5. PRD 预计超过 3000 字
6. 需要 2 个以上专项文档
7. 研发需要明显分成不同小组开发

### 需要重新合并的信号

如果拆分后每个 PRD 只有一两个字段变化，且属于同一页面或同一链路，应重新合并。

不要为了拆而拆。拆分的目标是让研发好理解、好开发、好验收，不是让文档变多。

---

## 七、需求包交付物裁剪规则

### 小需求包（≤ 3 个需求项，且不涉及 AI、状态机、多页面）

至少生成：

```
00_交付物与章节规划.md
03_PRD_产品需求文档.md
07_研发交付检查清单.md
```

PRD 使用简化模板，A 类章节合并简化。

### 中大型需求包（> 3 个需求项，或涉及 AI、状态机、多页面）

按原有规则生成：

```
00_交付物与章节规划.md
01_BRD_业务需求说明.md        （按交付物启用规则判断）
02_需求分析与范围定义.md      （按交付物启用规则判断）
03_PRD_产品需求文档.md
04_PRD_专项文档/              （有外拆时）
05_原型说明文档.md            （按交付物启用规则判断）
06_HTML原型生成提示词.md      （按交付物启用规则判断）
07_研发交付检查清单.md
```

### 判断规则

需求包复杂度判断不是简单数需求项数量，而是综合判断：

| 维度 | 小需求包 | 中大型需求包 |
|------|---------|------------|
| 需求项数量 | ≤ 3 | > 3 |
| 涉及 AI | 否 | 是（或部分） |
| 涉及状态机 | 否 | 是 |
| 涉及多页面 | 否（≤ 1 页面） | 是 |
| 涉及支付/订单/权限 | 否 | 是 |
| 需要原型说明 | 否 | 是 |

满足任一"中大型"维度，即按中大型需求包处理。

---

## 八、需求归组执行流程

当一次输入多个需求时，按以下流程执行：

### Step A：识别需求项

列出用户输入中的所有需求项。

```markdown
## 需求项清单

| 编号 | 需求描述 | 初步判断类型 |
|------|----------|------------|
| 1 | 分销记录列表增加搜索用户功能 | 小迭代 |
| 2 | 分销记录展示用户头像和昵称 | 小迭代 |
| 3 | 团队人数列表展示用户电话 | 小迭代 |
| 4 | 活动订单列表新增订单状态 | 状态流转 + 小迭代 |
| 5 | 活动订单支持按支付方式筛选 | 小迭代 |
| 6 | 首页 Banner 点击跳转会员页面 | 小迭代 |
```

### Step B：判断归组

按"适合合并"和"应该拆分"规则，对需求项进行归组。

```markdown
## 需求归组结果

| 需求包 | 包含需求项 | 归组依据 |
|--------|-----------|----------|
| 需求包01：分销页面优化 | 1, 2, 3 | 同模块（分销），同页面组 |
| 需求包02：活动订单管理优化 | 4, 5 | 同模块（活动订单），同操作链路 |
| 需求包03：Banner跳转优化 | 6 | 独立小需求，与其他需求无关联 |
```

### Step C：创建版本文件夹

按命名格式创建版本文件夹。

### Step D：按需求包生成交付物

每个需求包单独进入原有的 7 步工作流，交付物放入对应需求包文件夹。

---

## 九、示例

### 示例 1：应合并的需求

用户输入：

```
后台管理系统：分销记录列表增加搜索用户、展示用户头像和昵称、列表空状态设计
```

**判断**：这 3 个需求都属于同一个页面（分销记录列表），同一个模块（分销），同一个端口（后台），拆开会造成上下文断裂。

**结果**：合并为 1 个需求包。

### 示例 2：应拆分的需求

用户输入：

```
1. AI 纪要生成增加重新生成按钮
2. 分销记录列表增加搜索功能
```

**判断**：需求 1 涉及 AI 生成链路，需求 2 是普通非 AI 功能，所属模块不同，业务目标不同，上线节奏可以独立。

**结果**：拆为 2 个需求包。需求 1 走 AI 功能预设；需求 2 走小迭代预设。

### 示例 3：多需求完整归组

用户输入：

```
本次哆爱宠要改几个点：
1. 分销记录列表增加搜索用户功能
2. 分销记录展示用户头像和昵称
3. 团队人数列表展示用户电话
4. 活动订单列表新增订单状态
5. 活动订单支持按支付方式筛选
6. 首页 Banner 点击跳转会员页面
```

归组结果：

```
outputs/V版本号_日期_哆爱宠分销与活动优化/
├── 需求包01_分销页面优化/
│   ├── 00_交付物与章节规划.md
│   ├── 03_PRD_产品需求文档.md
│   ├── 05_原型说明文档.md
│   └── 07_研发交付检查清单.md
├── 需求包02_活动订单管理优化/
│   ├── 00_交付物与章节规划.md
│   ├── 03_PRD_产品需求文档.md
│   ├── 05_原型说明文档.md
│   └── 07_研发交付检查清单.md
└── 需求包03_Banner跳转优化/
    ├── 00_交付物与章节规划.md
    ├── 03_PRD_产品需求文档.md
    └── 07_研发交付检查清单.md
```

归组依据：
- 需求 1、2、3 同属"分销"模块，同一页面组 → 需求包 01
- 需求 4、5 同属"活动订单"模块，同一操作链路（订单状态 + 支付方式筛选）→ 需求包 02
- 需求 6 独立于其他需求，模块不同（首页），业务目标不同 → 需求包 03
- 需求包 03 只有 1 个需求项，不需要原型说明，交付物裁剪为 3 件
