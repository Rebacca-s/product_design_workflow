# 产品业务逻辑评审规则

## 核心原则

> Review Agent 和 prd-review 在进行需求评审时，除了已有的 12 个检查维度外，还必须进行业务逻辑深度核验。业务逻辑评审的目的是发现角色权责错位、数据归属混乱、流程不闭环、页面归属错误和案例污染等问题。

---

## 一、角色权责检查

### 1.1 检查维度

对每一项关键业务数据和操作，检查：

```text
谁创建？
谁提交？
谁维护？
谁修改？
谁审核？
谁查看？
谁对结果负责？
```

### 1.2 判定标准

发现以下情况应列为问题：

| 问题类型 | 说明 | 严重级别 |
|----------|------|----------|
| 平台后台修改本应由业务主体维护的数据 | 数据产生端和维护端不一致 | P1 |
| 查看方获得了不合理的编辑权限 | 权限越界 | P1 |
| 审核方同时作为被审核方 | 利益冲突 | P0 |
| 数据产生端和数据维护端混乱 | 权责不清 | P1 |
| 多个角色可以无边界地修改同一核心数据 | 数据安全风险 | P0 |
| 操作入口放在不合理的端或页面 | 页面归属错误 | P1 |

### 1.3 检查输出格式

```markdown
### 角色权责矩阵

| 业务对象或数据 | 创建方 | 维护方 | 审核方 | 查看方 | 是否合理 | 问题说明 |
|---------------|--------|--------|--------|--------|----------|----------|
| [对象] | [角色] | [角色] | [角色] | [角色] | ✅/⚠️/❌ | [如有问题] |
```

## 二、数据归属检查

### 2.1 检查维度

检查每个关键字段：

| 检查项 | 说明 |
|--------|------|
| 数据来源 | 数据由哪个角色、页面或系统产生 |
| 数据维护方 | 谁可以持续修改 |
| 数据使用方 | 哪些模块读取该数据 |
| 权威来源 | 多端出现时以哪一端为准 |
| 同步方式 | 是否需要跨端同步 |
| 历史记录 | 是否需要保留修改记录 |

### 2.2 判定标准

| 问题类型 | 严重级别 |
|----------|----------|
| 数据来源未定义 | P1 |
| 多个权威来源冲突 | P0 |
| 数据维护方与数据产生方不一致且无合理解释 | P1 |
| 跨端数据不同步且未说明同步机制 | P1 |

### 2.3 检查输出格式

```markdown
### 数据来源与流转

| 数据 | 来源 | 维护方 | 使用方 | 权威来源 | 同步方式 | 问题 |
|------|------|--------|--------|----------|----------|------|
| [字段] | [来源] | [角色] | [模块] | [端] | [方式] | [如有] |
```

## 三、流程闭环检查（强化）

### 3.1 检查维度

除已有主流程闭环检查外，额外检查：

| 检查点 | 说明 |
|--------|------|
| 有创建但没有后续处理 | 数据产生后是否有下一步操作 |
| 有审核但没有提交入口 | 审核流程的起点是否明确 |
| 有状态但没有触发状态变化的操作 | 状态流转的触发条件是否定义 |
| 有结果展示但没有数据来源 | 展示的数据从哪里来 |
| 有下游展示但没有上游配置 | 配置和展示是否对应 |
| 删除、停用后，下游处理不明确 | 数据生命周期终止后的连锁影响 |
| 角色之间的交接节点缺失 | 多角色协作的交接点是否定义 |
| 主流程只描述页面，没有描述数据如何流转 | 是否停留在 UI 层面 |

### 3.2 检查输出格式

```markdown
### 流程闭环检查

| 流程节点 | 前置条件 | 操作角色 | 结果/产出 | 下一节点 | 是否闭环 | 问题 |
|----------|----------|----------|-----------|----------|----------|------|
| [节点] | [条件] | [角色] | [结果] | [下一节点] | ✅/❌ | [如有] |
```

## 四、状态流转检查（强化）

### 4.1 检查维度

每个状态必须核验：

```text
进入条件：什么情况下进入该状态？
可执行操作：该状态下可以做什么？
操作角色：谁可以执行操作？
退出条件：什么情况下离开该状态？
下一状态：可以流转到哪些状态？
异常处理：异常情况下如何处理？
是否可逆：状态是否可回退？
```

### 4.2 判定标准

| 问题类型 | 严重级别 |
|----------|----------|
| 只有状态名称，没有流转逻辑 | P0 |
| 存在不可达状态 | P0 |
| 存在死锁状态（进入后无法离开） | P0 |
| 缺少异常状态处理 | P1 |
| 可逆/不可逆未说明 | P2 |

---

## 五、页面归属检查

### 5.1 检查维度

检查功能入口是否放在正确的端：

```text
平台管理后台
业务操作后台
商家端
门店端
员工端
用户端
小程序或 App
```

### 5.2 判定标准

页面归属应与以下内容一致：

1. 角色职责 — 谁负责该业务
2. 数据维护权 — 谁维护该数据
3. 实际操作场景 — 谁在日常工作中使用该功能

### 5.3 常见问题

| 问题 | 说明 | 严重级别 |
|------|------|----------|
| 业务主体数据只能由平台修改 | 数据维护权错位 | P1 |
| 用户端功能入口放在管理后台 | 页面归属错误 | P1 |
| 审核功能放在被审核方端 | 利益冲突 | P0 |
| 配置功能放在无配置权限的角色端 | 权限越界 | P1 |

---

## 六、案例污染检查

### 6.1 检查维度

Review Agent 必须检查需求文档中是否存在以下问题：

| 检查点 | 说明 |
|--------|------|
| 运营案例写成固定产品规则 | 某次活动的规则被写成系统永久规则 |
| 某次运营活动写成长期系统机制 | 短期运营手段被固化为系统功能 |
| 当前配置值写成系统唯一允许值 | "三个月"被写成固定阈值 |
| 具体案例描述代替通用规则 | 大量使用"例如""比如"描述核心规则 |
| 研发无法区分功能规则和示例 | 功能规则和示例混在一起 |

### 6.2 判定标准

| 问题类型 | 严重级别 |
|----------|----------|
| 案例被写成系统固定规则，会导致研发错误实现 | P0 |
| 当前配置值被写成系统唯一允许值 | P1 |
| 运营策略被默认设计成强制流程 | P1 |
| 示例与正式规则混杂，难以区分 | P1 |
| 角色名称仅来自案例但被写成系统固定角色 | P1 |

### 6.3 检查输出格式

```markdown
### 案例与规则分离检查

| 内容位置 | 当前表述 | 是否被错误固化 | 问题说明 | 建议 |
|----------|----------|---------------|----------|------|
| [章节/段落] | [原文摘要] | ✅/❌ | [问题] | [修改建议] |
```

## 八、入口闭环检查（v1.1 新增）

### 8.1 核心原则

> **文档中出现的每一个按钮、链接、入口，都必须有对应的后续页面和完整链路。**
> 没有下游的入口 = 用户走进了一条死胡同。

### 8.2 检查维度

对文档中每一个交互入口，逐项检查：

```text
入口是什么？（按钮/链接/Tab/卡片点击）
    ↓
点击后去哪里？（页面/弹窗/选择器）
    ↓
目标页面设计了没有？（在页面清单中吗？有详细设计吗？）
    ↓
操作后的状态变化定义了吗？（状态流转有覆盖吗？）
    ↓
操作后的返回路径是什么？（用户怎么回到之前的页面？）
```

### 8.3 检查方法

**Step 1：提取所有入口**

扫描文档中出现的所有交互入口：
- 按钮（[加入购物车]、[立即购买]、[去评价]...）
- 链接（查看全部、更换门店、修改时间...）
- Tab切换
- 卡片点击
- 图标点击

**Step 2：逐个追踪下游**

对每个入口，在文档中查找对应的目标页面或处理逻辑。如果找不到，标记为遗漏。

**Step 3：分类处理**

| 情况 | 处理 |
|------|------|
| 入口在文档中但目标页面缺失 | P0 — 阻断，必须补充 |
| 入口在文档中但目标页面只有概要无详细设计 | P1 — 建议补充 |
| 入口在文档中且目标页面完整 | ✅ 通过 |
| 入口是现有功能的引用（非本次新增） | 标注为"复用现有"，不要求本次设计 |

### 8.4 常见遗漏模式

| 遗漏模式 | 示例 | 严重级别 |
|----------|------|----------|
| 详情页有[加入购物车]按钮，但没有购物车页面 | 用户点了按钮，不知道去了哪里 | P0 |
| 列表页有"查看全部"链接，但没有对应列表页 | 链接指向的页面不存在 | P0 |
| 订单卡片有[去评价]按钮，但评价表单页/评价成功页缺失 | 评价流程不完整 | P1 |
| 后台列表有[导出]按钮，但没有说明导出格式和交互 | 导出功能不可执行 | P1 |
| 按钮/链接的目标页面在跳转关系图中出现，但实际未设计 | 跳转图与实际不一致 | P1 |

### 8.5 判定标准

| 问题类型 | 严重级别 |
|----------|----------|
| 用户可见按钮/入口的目标页面完全缺失 | P0 |
| 目标页面在跳转图中出现但无详细设计 | P1 |
| 入口的反馈逻辑（点击后弹什么、跳哪里）未说明 | P1 |
| 编辑/操作按钮的操作后果未定义 | P1 |

### 8.6 检查输出格式

```markdown
### 入口闭环检查

| 入口位置 | 入口类型 | 入口文案 | 目标页面/操作 | 目标是否已设计 | 是否闭环 | 问题 |
|----------|----------|----------|-------------|--------------|----------|------|
| [页面/章节] | 按钮/链接/Tab | [文案] | [目标] | ✅/❌/⚠️ | ✅/❌ | [如有] |
```

## 九、需求文档质量检查

### 7.1 检查维度

| 检查点 | 说明 |
|--------|------|
| 是否明确区分已有功能和本次新增功能 | 研发需要知道哪些是新的 |
| 是否明确区分修改内容和保持不变的内容 | 避免误改 |
| 关键假设是否标记 | 【当前假设】标识 |
| 待确认事项是否标记 | 【待确认】标识 |
| 是否存在 AI 推断伪装成用户结论 | AI 推导必须标记 |
| 用户只要求局部修改时，是否遵守"未提到的内容不修改" | 防止范围蔓延 |

### 7.2 判定标准

| 问题类型 | 严重级别 |
|----------|----------|
| AI 推断被写成已确认事实，可能误导研发 | P0 |
| 待确认事项未标记，研发可能当作最终需求 | P1 |
| 修改范围不明确，可能影响无关模块 | P1 |

## 八、评审报告新增章节

在现有评审报告模板的"问题清单"和"一致性检查"之间，新增：

```markdown
---

## 业务逻辑核验

### 角色权责矩阵

| 业务对象或数据 | 创建方 | 维护方 | 审核方 | 查看方 | 是否合理 | 问题 |
|---------------|--------|--------|--------|--------|----------|------|

### 数据来源与流转

| 数据 | 来源 | 维护方 | 使用方 | 权威来源 | 问题 |
|------|------|--------|--------|----------|------|

### 流程闭环检查

| 流程节点 | 前置条件 | 操作角色 | 结果 | 下一节点 | 是否闭环 |
|----------|----------|----------|------|----------|----------|

### 页面归属检查

| 功能入口 | 当前归属端 | 角色职责 | 数据维护权 | 是否合理 | 问题 |
|----------|-----------|----------|-----------|----------|------|

### 案例与规则分离检查

| 内容位置 | 当前分类 | 是否被错误固化 | 建议 |
|----------|----------|---------------|------|
```

对于简单需求，可以缩减表格行数，但对应判断不得完全省略。
