# 前端页面规划与实现规则

## 核心原则

> Frontend Agent 不得收到需求后立即开始逐页编码。必须先识别任务类型、生成页面设计计划、分析现有代码、确定数据策略，再逐页实施。原型过程中发现的需求变更必须返回 Product Agent 同步。

---

## 一、前端任务类型识别

### 1.1 任务类型

Frontend Agent 开始工作前，必须判断本次属于哪一种任务：

| 任务类型 | 定义 | 默认处理方式 |
|----------|------|-------------|
| 全新页面原型 | 当前项目不存在对应页面 | 根据 PRD 和页面计划创建 |
| 已有页面增量修改 | 在现有页面增加字段、按钮、模块或交互 | 先分析现有页面，再增量修改 |
| 已有组件扩展 | 在现有组件上增加状态或能力 | 优先复用和扩展现有组件 |
| 纯原型演示 | 用于需求评审，不接真实后端 | 使用可控 Mock 数据和状态模拟 |
| 接口联调实现 | 已有明确接口，需要按接口实现 | 优先遵守真实接口结构 |
| 混合模式 | 已有页面和接口，但新增字段尚无后端支持 | 真实数据与原型 Mock 隔离 |
| 样式修复 | 仅调整布局、样式或交互一致性 | 不修改业务逻辑 |
| 需求补漏 | 原型过程中发现 PRD 缺失 | 暂停直接实现，进入需求同步流程 |

### 1.2 输出格式

```markdown
## 前端任务识别

| 项目 | 内容 |
|------|------|
| 任务类型 | [类型] |
| 是否存在现有页面 | [是/否] |
| 是否存在真实接口 | [是/否] |
| 是否需要 Mock 数据 | [是/否，原因] |
| 是否影响原有功能 | [是/否] |
| 是否需要先同步需求 | [是/否] |
```

## 二、强制页面设计计划

### 2.1 核心规则

> Frontend Agent 不得收到需求后立即开始逐页编码或画原型。必须先生成一份可持续维护的页面设计与实现计划。

### 2.2 计划交付物

建议路径：`outputs/对应需求名称/08_前端页面实施与进度计划.md`

> 该计划不是新的产品页面设计文档，不重新定义页面、字段、交互和业务规则。它只记录产品交付物与前端页面的对应关系、实现方式、进度和原功能保护范围。

### 2.3 计划内容

```markdown
# 前端页面实施与进度计划

## 一、目标与范围
- 本次目标：
- 本次新增：
- 本次修改：
- 保持不变：
- 不在本次范围：

## 二、业务流程对应关系
【说明每个页面处于业务流程的哪个节点】

## 三、页面清单
| 编号 | 页面或弹窗 | 所属端 | 类型 | 来源需求 | 前置依赖 | 状态 | 完成情况 |

## 四、公共组件清单
| 组件 | 使用页面 | 是否已有 | 处理方式 |

## 五、状态与数据形态清单
| 页面或组件 | 状态或形态 | 是否需要可视化切换 | 实现方式 |

## 六、交互清单
| 页面 | 操作 | 预期结果 | 是否必须可点击 | 优先级 |

## 七、实现批次
| 批次 | 页面范围 | 依赖关系 | 当前状态 |

## 八、遗留问题
| 问题 | 是否阻塞 | 当前处理 |
```

### 2.4 持续维护

每完成一个页面、弹窗、状态或交互后，必须更新计划中的：
- 当前完成状态
- 已实现内容
- 尚未完成内容
- 新发现的问题
- 下一步任务
- 是否影响后续批次

每轮回复结束前必须检查：

```text
1. 页面总数是多少？
2. 已完成多少？
3. 正在处理哪个页面？
4. 后续还有哪些页面？
5. 是否因本轮修改影响后续计划？
6. 是否有页面被遗漏？
```

## 三、业务流程与页面映射

### 3.1 核心规则

> 前端页面不能只根据页面名称独立设计。必须先梳理业务主线：数据从哪里产生 → 由谁创建或配置 → 在哪个页面维护 → 经过哪些状态和审核 → 由哪些下游页面读取 → 最终展示给谁。

### 3.2 输出格式

```markdown
## 页面与业务流程映射

| 流程节点 | 数据来源 | 操作角色 | 对应页面 | 结果去向 |
|----------|----------|----------|----------|----------|
```

### 3.3 阻断条件

发现以下问题时不得直接继续画页面，应返回 Product Agent 或 Review Agent：
- 页面展示了数据但没有上游创建入口
- 存在新增对象但没有新增或配置页面
- 存在状态结果但没有触发状态变化的操作
- 下游页面读取数据但没有明确权威数据来源
- 不同端之间的数据流转未说明
- 页面只展示最终结果，没有体现主流程

## 四、已有接口与 Mock 数据适配

### 4.1 数据来源区分

必须明确区分：

| 数据类型 | 说明 | 处理方式 |
|----------|------|----------|
| 真实接口数据 | 后端已支持的接口 | 保留，不替换 |
| 原型演示数据 | 仅用于原型展示 | 独立 Mock 文件或适配层 |
| 前端临时补充数据 | 接口暂未返回的字段 | 在适配层补充，标记待对接 |
| 后端待新增字段 | PRD 要求但后端未实现 | Mock 隔离，明确标记 |

### 4.2 Mock 隔离方式

推荐以下方式之一（根据项目技术栈选择）：
- 独立 Mock 文件
- 独立 demo 数据层
- 显式 prototype mode 开关
- 独立状态演示组件
- 前端适配函数（真实响应 + 补充字段）
- 仅开发环境生效的增强数据

### 4.3 数据来源说明

每个关键页面必须说明数据来源：

```markdown
## 页面数据来源

| 页面元素 | 数据字段 | 当前来源 | 原型处理 | 正式研发要求 |
|----------|----------|----------|----------|-------------|
```

### 4.4 禁止事项

- 为了展示新增状态，删除或替换已有接口
- 将 Mock 数据写入生产逻辑
- 将新增前端字段伪装成后端已返回字段
- 在未说明的情况下改动接口字段含义
- 因为接口缺失而重写整个页面的数据逻辑
- 破坏原有真实数据的正常展示

## 五、多状态与多数据形态模拟

### 5.1 触发条件

页面存在以下任一情况时，必须提供状态演示入口：
- 多业务状态
- 多审核状态
- 多角色权限
- 多种数据量级
- 不同组件数量
- 空数据与有数据
- 正常与异常
- 可操作与只读
- 不同接口结果

### 5.2 演示控制区

原型中应提供明确的演示控制区：

```
原型状态演示：[默认状态] [空状态] [审核中] [已通过] [已驳回] [无权限] [接口异常]
数据形态：[1个] [2个] [3个] [大量数据]
```

### 5.3 边界规则

- 状态演示入口只用于需求评审和原型展示
- 必须在代码或页面上明确标识"原型演示控制"
- 不直接成为正式产品功能
- 正式上线前可安全移除或关闭

### 5.4 状态完整性

每个关键页面至少判断是否需要展示：

| 状态 | 是否需要展示 | 触发方式 |
|------|-------------|----------|
| 首次进入 | | |
| 正常有数据 | | |
| 空状态 | | |
| 查询无结果 | | |
| Loading | | |
| 保存中 | | |
| 成功 | | |
| 失败 | | |
| 禁用 | | |
| 无权限 | | |
| 接口异常 | | |
| 业务状态差异 | | |

## 六、交互闭环要求

### 6.1 核心规则

> 前端原型不能只展示视觉结构。可操作元素原则上必须具备真实可点击反馈，形成完整的前端交互闭环。

### 6.2 交互优先级

**P0 — 必须可用**：主流程按钮、新增/编辑/删除、弹窗与抽屉、表单提交和校验、页面核心状态切换、关键 Tab、查询和重置、业务流程下一步操作

**P1 — 应尽量可用**：分页、排序、展开收起、批量选择、辅助设置、常用次级操作

**P2 — 可以仅展示**：尚未进入本次范围的入口、纯说明性按钮、外部系统跳转、依赖真实后端的复杂操作。如仅展示需标注："当前为展示入口，本次原型不实现具体逻辑。"

### 6.3 标准交互闭环

新增流程：点击新增 → 打开弹窗 → 填写表单 → 触发表单校验 → 点击保存 → 展示保存中 → 成功提示 → 关闭弹窗 → 列表出现新增数据

删除流程：点击删除 → 二次确认 → 确认删除 → 提示成功 → 列表移除该数据

筛选流程：输入或选择条件 → 点击查询 → 列表数据变化 → 点击重置 → 恢复默认数据

### 6.4 禁止出现

- 明显按钮点击无反应
- 弹窗无法关闭
- 表单保存后没有结果
- 筛选条件不会影响数据
- Tab 只是视觉按钮但无法切换
- 删除没有确认和结果反馈

## 七、已有页面增量适配

### 7.1 前置分析

在已有页面上增加内容时，必须先检查：

```text
1. 同页面已有布局
2. 同类型组件
3. 表单栅格和间距
4. Label 宽度和对齐方式
5. Input、Select 等组件规格
6. placeholder 规则
7. 必填标识方式
8. 校验触发时机
9. 错误提示形式
10. 按钮尺寸、层级和位置
11. 弹窗宽度和底部按钮结构
12. 表格列样式
13. 空状态和 Loading
14. 状态标签样式
15. 页面已有命名和文案习惯
```

### 7.2 组件样式继承

| 新增类型 | 应继承的内容 |
|----------|-------------|
| 新增表单字段 | Label样式、是否必填、placeholder格式、字数限制、格式校验、失焦/提交校验、错误提示、默认值、禁用状态、表单间距、帮助提示 |
| 新增表格列 | 对齐方式、宽度规则、空值展示、状态标签、操作列样式、超长文本处理、Tooltip、固定列规则 |
| 新增弹窗 | 标题结构、宽度、关闭方式、底部按钮顺序、保存状态、取消确认、表单校验 |
| 新增按钮 | 主次按钮层级、尺寸、图标使用方式、禁用逻辑、Loading、危险操作样式、位置和间距 |

### 7.3 设计规范扫描

新增 Step：现有设计与组件规范扫描。负责：
- 找到同类型页面作为参照
- 找到同类型组件作为参照
- 找到可复用 CSS/SCSS/组件/工具函数
- 总结当前页面设计规范
- 决定复用、扩展或新建

输出格式：

```markdown
## 现有设计适配分析

| 新增内容 | 参考对象 | 复用方式 | 是否新增样式 |
|----------|----------|----------|-------------|
```

## 八、原功能保护

### 8.1 核心规则

> 本次需求未明确要求修改的原有功能，应保持正常展示和正常交互。

### 8.2 保护清单

```markdown
## 原功能保护清单

| 原有功能 | 本次是否修改 | 保护要求 |
|----------|-------------|----------|
| 原列表展示 | 否 | 保持原数据渲染 |
| 原筛选条件 | 否 | 保持可用 |
| 原详情入口 | 否 | 保持跳转 |
| 原接口调用 | 否 | 不替换 |
```

### 8.3 回归检查

修改完成后必须检查：
- 原页面是否正常打开
- 原接口是否正常调用
- 原数据是否正常展示
- 原按钮是否仍可点击
- 原筛选是否仍有效
- 原表单校验是否仍存在
- 原路由是否正常
- 原权限判断是否保留
- 原响应式布局是否被破坏
- 原页面是否出现控制台错误

### 8.4 修改范围控制

```markdown
## 前端修改范围

### 本次新增
### 本次修改
### 保持不变
### 不在本次范围
### 预计涉及文件
### 不应涉及文件
```

若需修改超出范围的文件，先说明原因。不得以"顺便优化"为由重构无关代码。

## 九、需求与原型一致性

### 9.1 核心规则

> Frontend Agent 不得自行补充新的业务规则。

### 9.2 需求变更识别

原型实现过程中发现以下情况时，判断是否属于需求变更：
- 新增字段、角色权限、状态、业务流程、审核规则、操作入口、异常处理
- 修改已有规则、数据来源、页面归属
- 改变接口字段含义

### 9.3 需求同步流程

```
发现原型与需求不一致
    ↓
记录差异
    ↓
判断是否为业务需求变更
    ↓
返回 Product Agent
    ↓
修改 PRD 和相关交付物
    ↓
Review Agent 检查
    ↓
重新进入 Frontend Agent
```

### 9.4 原型阶段需求补漏

用户在原型阶段提出新需求时：

**A. 纯视觉或已有规则内小调整**（调整间距、增加说明文字、沿用已有字段展示、修复漏画但 PRD 已明确的元素）→ 可以直接修改原型

**B. 业务需求补充或变更**（新增业务字段、状态、权限、操作、改变业务规则、新增流程节点）→ 必须走需求同步流程

输出格式：

```markdown
## 原型阶段需求差异

| 用户提出内容 | PRD 是否已有 | 类型 | 处理方式 |
|-------------|-------------|------|----------|
| [内容] | 是/否 | A/B | [处理方式] |
```

## 十、页面完整性检查

每个页面生成完成后必须检查：

```text
页面入口是否存在
页面标题是否明确
页面主要区域是否完整
数据来源是否明确
筛选区是否完整
列表或内容区是否完整
操作入口是否完整
表单字段是否完整
状态是否完整
空状态是否完整
交互是否可用
返回路径是否存在
前后页面是否衔接
```

## 十一、原型与正式开发边界

| 维度 | 原型模式 | 正式实现模式 |
|------|----------|-------------|
| 目标 | 需求评审 | 上线交付 |
| 数据 | Mock 可控数据 | 真实接口 |
| 权限 | 模拟角色切换 | 真实权限 |
| 状态 | 演示切换 | 真实状态流转 |
| 编译 | 可以仅展示 | 必须通过编译 |
| 原型控制 | 可以有演示入口 | 无演示入口 |

frontend-implement 开始时必须判断当前是哪一种模式。
