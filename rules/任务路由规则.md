# 任务路由规则

## 核心原则

> 用户的每一次输入，都必须先进行任务识别和路由。不允许在未完成任务分类的情况下直接修改需求、文档或代码。

本规则是 Master Agent 进行任务路由的最高优先级依据。

---

## 一、路由决策流程

```text
用户输入
    ↓
1. 语义理解：用户想完成什么？
    ↓
2. 能力匹配：属于哪个能力领域？
    ↓
3. 关键词辅助：匹配自动触发关键词
    ↓
4. Agent 选择：由哪个 Domain Agent 承接？
    ↓
5. Skill 选择：需要执行哪个 Skill？
    ↓
6. 上下文检查：需要读取哪些文件？
    ↓
7. 变更判断：是否涉及文件修改？
    ↓
8. 确认判断：是否需要用户确认？
    ↓
9. 阶段判断：是否为多阶段任务？
    ↓
输出路由结果 → 执行
```

---

## 二、路由决策优先级

决策时按以下优先级判断：

| 优先级 | 决策来源 | 说明 |
|--------|----------|------|
| 1 | 用户明确指令 | 用户明确说"生成 PRD"、"改前端代码"、"检查需求" |
| 2 | 任务事实特征 | 输入内容涉及页面、字段、代码、文件等客观事实 |
| 3 | 关键词匹配 | 匹配自动触发关键词表（见 capability-registry.md） |
| 4 | 上下文推断 | 结合对话历史推断用户意图 |
| 5 | 默认兜底 | 无法判断时进入 General Agent，同时向用户确认 |

## 三、自动触发规则

### 3.1 产品需求类自动触发

以下任意条件满足时，路由到 **Product Agent → product-start**：

1. 用户输入涉及页面结构调整（"增加一个按钮"、"这个列表加个字段"）
2. 用户输入涉及业务规则变更（"这个状态流转改一下"、"权限需要调整"）
3. 用户输入涉及字段定义（"这个字段要不要保留"、"需要增加什么字段"）
4. 用户输入涉及流程设计（"这个流程怎么设计"、"订单状态怎么流转"）
5. 用户输入涉及交互规则（"点击后弹窗"、"筛选条件怎么放"）
6. 用户输入涉及异常处理（"网络异常怎么处理"、"空状态显示什么"）
7. 用户输入涉及角色权限（"管理员能看到什么"、"店长有哪些权限"）
8. 用户明确要求生成或修改 PRD/需求文档
9. 用户说"按我说的修改后完整发我"（上下文为需求讨论时）
10. 用户说"前面设计的逻辑有问题"或类似表述

### 3.2 PRD 评审类自动触发

以下任意条件满足时，路由到 **Review Agent → prd-review**：

1. 用户输入包含"检查"、"审核"、"评审"、"review"
2. 用户输入包含"有没有问题"、"逻辑合理吗"、"有漏洞吗"
3. 用户输入包含"是否完整"、"有没有遗漏"、"会不会冲突"
4. 用户询问"研发能不能直接做"、"测试能不能写用例"

### 3.3 前端实现类自动触发

以下任意条件满足时，路由到 **Frontend Agent → frontend-implement**：

1. 用户输入包含"写页面"、"改前端"、"修改代码"、"实现"
2. 用户输入包含"开发"、"落地"、"修复页面"
3. 用户输入包含"根据 PRD" + "开发/实现/修改"
4. 用户指定了具体的代码文件路径并要求修改

### 3.4 通用问答类自动触发

以下条件满足时，路由到 **General Agent**：

1. 不匹配以上任何能力
2. 用户询问概念解释、方法论、行业知识
3. 简单的确认性问答

## 四、多意图拆分规则

当用户一句话包含多个意图时，按以下规则拆分：

### 4.1 识别多意图的信号

- 连接词："然后"、"之后再"、"顺便"、"同时"、"并且"
- 复合句式："先...再..."、"...之后..."
- 多动词结构："检查需求，没问题就开始改前端"

### 4.2 拆分与排序

1. 拆分为独立的任务单元
2. 识别任务之间的依赖关系
3. 按依赖关系排序（前置任务先执行）
4. 每个任务独立路由

### 4.3 常见组合模式

| 用户输入 | 拆分 | 顺序 |
|----------|------|------|
| "检查需求，没问题就改前端" | Review → Frontend | 先 Review，通过后 Frontend |
| "改完需求后帮我检查" | Product → Review | 先 Product，再 Review |
| "分析这个需求然后生成 PRD" | Product（分析）→ Product（生成） | 同 Agent 内分阶段 |
| "这个功能怎么设计，顺便给我看看有没有问题" | Product → Review | 先 Product，再 Review |

---

## 五、路由覆盖规则

### 5.1 用户明确指定时

如果用户明确说"用 product-start"、"执行 PRD 评审"，以用户明确指令为准，但仍需经过 Master Agent 确认路由合理性。

### 5.2 路由冲突时

如果同时匹配多个能力，按以下规则处理：

1. 如果匹配项之间有依赖关系（如 Product → Review），按依赖顺序执行
2. 如果匹配项之间无依赖关系，优先选择与当前对话上下文最相关的能力
3. 如果无法确定，向用户确认意图

### 5.3 路由错误恢复

如果执行过程中发现路由错误（如 Product Agent 发现任务实际是代码修改），应：

1. 停止当前执行
2. 返回 Master Agent
3. Master Agent 重新路由
4. 说明路由变更原因

---

## 六、禁止的路由行为

1. ❌ 不经过路由，直接回答或修改
2. ❌ 识别为产品需求，但不经过 Product Agent 和 product-start
3. ❌ 识别为前端实现，但不经过 Frontend Agent 和 frontend-implement
4. ❌ 识别为评审任务，但不经过 Review Agent 和 prd-review
5. ❌ 多阶段任务跳过前置阶段
6. ❌ 因为用户没有输入 Skill 名称，就跳过 Skill

---

## 七、路由状态展示

每次路由完成后，必须在回复开头展示路由结果。格式见 `rules/Agent与Skill调用规则.md`。
