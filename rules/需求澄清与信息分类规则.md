# 需求澄清与信息分类规则

## 核心原则

> Product Agent 在正式设计需求前，必须先完成需求信息分类、抽象和关键澄清。不得将用户的所有描述直接当作正式需求，不得在需求未澄清的情况下直接进入交付物规划。

---

## 一、需求信息分类

### 1.1 分类标准

Product Agent 接收到用户输入后，必须先将信息拆分为以下类别：

| 信息类型 | 定义 | 在产品设计中的处理方式 |
|----------|------|------------------------|
| 已确认业务事实 | 当前系统、组织或业务已经真实存在的内容 | 作为设计约束 |
| 用户明确需求 | 用户明确要求新增或修改的产品能力 | 写入需求范围 |
| 业务目标 | 希望解决的问题或达成的结果 | 用于判断功能合理性 |
| 运营策略 | 业务人员实际采用的运营手段 | 不默认固化为系统规则 |
| 示例或案例 | 为帮助理解而举出的具体例子 | 仅作为说明，不默认写成通用规则 |
| 用户假设 | 用户推测、尚未确认的内容 | 标记为待确认或设计假设 |
| AI 推导 | Claude Code 根据上下文作出的推断 | 必须明确标记，不得伪装成用户结论 |
| 待澄清事项 | 会影响方向、角色、流程、权限、数据或范围的问题 | 进入需求澄清 |

### 1.2 分类输出格式

```markdown
## 需求理解与信息分类

### 业务目标
【用户真正想解决的问题】

### 核心产品能力（抽象后）
【抽象后的通用功能描述】

### 已确认业务事实
【当前已经存在的角色、流程、页面或规则】

### 用户明确要求
【本次需要新增或修改的内容】

### 运营策略（不默认固化为系统规则）
【仅属于运营方式的内容】

### 示例与案例（仅用于说明）
【用户用于帮助理解的例子】

### 当前假设
【允许先按假设继续设计的内容】

### 待澄清事项
【需要向用户确认的关键问题】
```

对于简单需求，可以压缩为对话输出；对于复杂需求，建议作为阶段输出。

## 二、案例与产品规则强制分离

### 2.1 核心规则

> 用户举出的业务案例、角色名称、运营玩法或实际操作方式，默认用于帮助理解，不自动等于产品通用规则。

### 2.2 示例

用户说：
```
例如 KA 服务商给 Pro 服务商配置某项会员权益。
```

**错误处理**：直接得出"系统只需要支持 KA 服务商和 Pro 服务商"。

**正确处理**：
1. 抽象为："系统需要支持上级业务角色为下级业务角色配置某类权益或规则"
2. "KA 服务商、Pro 服务商"标记为当前业务案例或当前业务角色
3. 询问该能力是否仅适用于 KA/Pro，还是需要通用化

### 2.3 案例固化的三个条件

只有在以下情况下，才能将案例内容正式写入产品规则：

1. 用户明确说明该角色或规则就是系统固定设计
2. 现有业务上下文已经证明其为正式业务对象
3. 经过需求澄清后，用户确认应固化为产品规则

### 2.4 禁止行为

1. 运营人员当前怎么操作，不等于系统必须按该方式固化
2. 当前某个客户的做法，不等于所有客户都适用
3. 当前某个角色名称，不等于产品只能支持该角色
4. 当前一次活动规则，不等于长期产品规则
5. 用户举出的数字、金额、比例或角色关系，除非明确确认，否则只作为案例

## 三、需求抽象规则

### 3.1 抽象维度

需求抽象是 Product Agent 内部的必要阶段。至少回答：

```text
1. 用户真正想解决的业务问题是什么？
2. 当前案例背后的通用能力是什么？
3. 哪些内容是固定业务规则？
4. 哪些内容只是当前运营做法？
5. 哪些内容只是例子？
6. 是否需要做成可配置能力？
7. 功能适用于单一角色，还是适用于一类角色？
8. 需求中有哪些隐含假设？
```

### 3.2 抽象示例

| 用户描述 | 抽象后的产品能力 | 标记为案例/运营的内容 |
|----------|-----------------|----------------------|
| "KA 服务商给 Pro 服务商配置会员权益" | 上级业务角色为下级业务角色配置权益 | KA、Pro 为当前业务角色 |
| "运营给连续三个月没下单的用户发优惠券" | 系统支持按用户行为条件筛选并触发营销动作 | "三个月"为当前配置值 |
| "门店自己管理营业时间" | 支持门店端维护自身业务状态 | 具体业务对象为"门店" |

## 四、AI 自主判断原则

### 4.1 自主判断范围

以下类型的问题，Product Agent 应优先根据行业通用实践、项目已有规范和业务上下文自主做出合理方案，不应主动询问用户：

#### 页面基础设计
- 列表默认排序（默认按创建时间倒序）
- 分页方式
- 常规筛选布局
- 搜索框位置
- 表单字段排列方式
- 普通按钮位置
- 常见空状态设计
- Loading 状态设计
- 常规校验提示

#### 通用业务逻辑
- 新增数据后返回列表
- 删除前二次确认
- 停用数据不直接删除
- 已完成状态不可修改核心字段
- 创建时间、更新时间自动记录
- 普通列表支持分页
- 查询条件支持组合筛选
- 权限不足不可操作

#### 常规角色和权限判断
- 后台管理系统：管理员负责配置和管理，普通业务人员负责日常操作
- AI 可根据业务场景判断合理角色，先给出符合业务习惯的设计

### 4.2 必须向用户确认的问题

只有以下情况，必须询问产品经理：

1. **影响业务目标的问题**：功能解决什么问题、是内部使用还是开放给客户
2. **存在多个合理方案的问题**：AI 无法根据上下文判断唯一合理方案
3. **涉及业务权责的问题**：谁产生数据、谁维护数据、谁拥有最终修改权、谁承担业务责任
4. **涉及商业规则的问题**：分佣比例、会员权益、优惠规则、结算方式、审核标准、风控规则
5. **已有系统约束不明确的问题**：是否已有接口、是否已有页面、是否兼容历史数据、是否影响已有流程

### 4.3 确认问题的格式

不允许只提出开放问题。必须先分析，再提供推荐方案：

```markdown
## 需要确认的问题

### 问题：[问题描述]

### AI 分析：
根据常见产品设计实践：

推荐方案：方案 A（推荐）
- [方案描述]
- 原因：[理由]

方案 B：
- [方案描述]
- 适合：[适用场景]

### 请确认：
A. 采用方案 A（推荐）
B. 采用方案 B
C. 其他方案
```

## 五、澄清问题分级

### 5.1 必须确认的问题

如果答案不同会直接改变以下任一内容，则必须询问用户：

- 业务目标
- 功能范围
- 使用角色
- 数据产生方
- 数据维护方
- 操作权限
- 核心业务流程
- 状态流转
- 页面归属
- 系统边界
- 与现有业务的关系
- 是否影响订单、支付、审核、结算、库存、权限或用户权益
- 当前功能是否已经存在
- 本次是新增、修改、替换还是补充
- 是否需要兼容历史数据或现有流程

### 5.2 可以按假设继续的问题

以下低风险事项通常不需要反复询问：

- 按钮文案
- 普通提示语
- 常规列表布局
- 默认排序方式
- 常规分页条数
- 沿用现有设计规范的样式
- 不影响业务逻辑的交互细节

对于此类内容，可以明确写出假设后继续：

```text
当前假设：新增字段沿用现有页面同类型字段的展示和校验规范。
```

## 六、澄清轮次限制

### 6.1 轮次规则

| 轮次 | 澄清内容 | 限制 |
|------|----------|------|
| 第一轮 | 业务方向、角色、范围、流程和权责 | 不超过 8 个问题 |
| 第二轮 | 仅澄清仍然阻塞设计的关键问题 | 不超过 5 个问题 |
| 超过两轮 | 除非存在高风险业务冲突，否则进入明确假设模式 | — |

### 6.2 提问原则

- 优先提出会影响设计方向的问题
- 可以合并的问题不要拆开询问
- 已能通过上下文确定的内容不要重复询问
- 不因按钮文案、普通样式等小问题阻断需求设计

### 6.3 用户选择

每轮澄清后应给用户选择：

```markdown
A. 先回答必须确认的问题
B. 按当前假设生成 v0.1
C. 修改或补充需求描述
```

## 七、已有业务功能核验

### 7.1 核验清单

当需求涉及已有产品或已有页面时，Product Agent 必须先核验：

```text
1. 当前已经有哪些功能？
2. 当前页面入口在哪里？
3. 当前由哪个角色使用？
4. 当前数据从哪里产生？
5. 当前数据由谁维护？
6. 当前有哪些状态？
7. 当前是否已有相关接口、字段或权限？
8. 本次是新增还是修改？
9. 本次会影响哪些已有模块？
10. 哪些原有内容必须保持不变？
```

### 7.2 信息来源优先级

1. 先读取 `context/products/` — 产品业务上下文
2. 再读取 `outputs/` — 已有交付物
3. 再读取 `local_projects/frontend/` — 前端代码（理解现状）
4. 最后才向用户提问（仅当以上来源无法覆盖且影响核心设计时）

---

## 八、禁止运营手段污染通用需求

### 8.1 强制规则

1. 运营人员当前怎么操作，不等于系统必须按该方式固化
2. 当前某个客户的做法，不等于所有客户都适用
3. 当前某个角色名称，不等于产品只能支持该角色
4. 当前一次活动规则，不等于长期产品规则
5. 用户举出的数字、金额、比例或角色关系，除非明确确认，否则只作为案例
6. PRD 正文优先写通用产品规则
7. 具体业务案例可放在"示例"或"业务举例"中

### 8.2 需求文档中的推荐结构

```markdown
### 功能规则
【系统长期支持的能力】

### 可配置项
【可以由业务人员配置的内容】

### 当前业务配置
【当前实际采用的值】

### 示例
【仅用于帮助理解，不作为固定规则】
```

### 8.3 研发必须能清晰区分

- 系统规则
- 可配置项
- 当前配置值
- 运营案例
- 示例数据

不得在没有区分的情况下，将案例内容散落在正式规则中。

---

## 九、需求文档生成标识

生成 PRD 时，对关键业务规则建议使用以下标识区分状态：

| 标识 | 含义 |
|------|------|
| 【已确认】 | 用户明确确认的内容 |
| 【当前假设】 | AI 基于行业实践做出的设计假设 |
| 【待确认】 | 需要用户确认的内容 |
| 【示例】 | 仅用于帮助理解的例子 |
| 【现有功能】 | 已有系统中存在的功能 |
| 【本次新增】 | 本次需求新增的内容 |
| 【本次修改】 | 本次需求修改的内容 |
| 【保持不变】 | 明确不受本次修改影响的内容 |

不要求每句话都添加标识，但关键业务规则必须能够区分其状态。
