# 禁止绕过工作流规则

## 核心原则

> 任何涉及产品需求、业务规则、页面、字段、流程、状态、权限、交互或代码修改的任务，必须经过对应的工作流。不存在完全无约束的直接回复路径。

---

## 一、全局禁止行为

以下行为在**任何情况**下均被禁止：

### 1.1 产品需求相关禁止行为

| 编号 | 禁止行为 | 说明 |
|------|----------|------|
| P01 | 未声明任务类型，直接修改 PRD | 必须先路由，再修改 |
| P02 | 未进入 Product Agent，直接新增或修改产品需求 | 即使是"小修改"也必须经过 Product Agent |
| P03 | 未经过 product-start 方法论，直接生成完整需求文档 | 必须经过需求识别→规划→装配的流程 |
| P04 | 未经过需求澄清规则，直接根据模糊信息生成全部交付物 | 信息不足时先澄清或写假设 |
| P05 | 将用户一句局部修改理解成可任意扩展需求 | "改这里"就是改这里，不扩展范围 |
| P06 | 在产品讨论中直接修改前端代码 | 产品讨论归 Product Agent，代码归 Frontend Agent |

### 1.2 前端修改相关禁止行为

| 编号 | 禁止行为 | 说明 |
|------|----------|------|
| F01 | 未进入 Frontend Agent，直接修改前端代码 | 即使只是一行 CSS |
| F02 | 在需求不清楚时自行补充业务规则后实施 | 必须回传 Product Agent |
| F03 | Frontend Agent 自行重新定义产品需求 | 发现需求问题→返回 Review/Product Agent |
| F04 | 在没有修改计划的情况下直接改代码 | 必须先出计划（除非用户说"直接执行"） |

### 1.3 评审相关禁止行为

| 编号 | 禁止行为 | 说明 |
|------|----------|------|
| R01 | 评审请求不经过 Review Agent 的检查框架 | 不能以"我觉得没问题"代替系统化评审 |
| R02 | Review Agent 未经授权直接改写需求 | 默认只输出问题和建议 |
| R03 | 评审时只检查部分维度 | 必须覆盖全部 12 个检查维度 |

### 1.4 通用禁止行为

| 编号 | 禁止行为 | 说明 |
|------|----------|------|
| G01 | 未说明 Skill 调用情况，直接结束回复 | 每次回复必须有调用汇总 |
| G02 | 因为用户没有输入 Skill 名称，就跳过 Skill | 路由和调用由系统自动完成 |
| G03 | 存在完全无分类的直接回答 | 即使是"你好"也要经过 General Agent |
| G04 | 跳过前置阶段直接执行后续阶段 | 多阶段任务必须按顺序执行 |

## 二、最小化流程要求

### 2.1 产品需求修改的最小流程

即使是"把这里改一下"这样的微小修改，也必须至少经过：

```text
Master Agent 路由（识别为产品需求修改）
    ↓
Product Agent 承接
    ↓
上下文读取（相关 PRD、页面说明、字段定义）
    ↓
影响分析（这个修改影响哪些内容？）
    ↓
执行修改（只改受影响的内容）
    ↓
一致性检查（PRD、页面说明、字段是否一致？）
    ↓
输出结果 + 调用汇总
```

### 2.2 前端修改的最小流程

即使是"改一个按钮颜色"这样的微小修改，也必须至少经过：

```text
Master Agent 路由（识别为前端实现）
    ↓
Frontend Agent 承接
    ↓
确认需求来源（基于哪个 PRD/需求文档？）
    ↓
定位文件
    ↓
执行修改
    ↓
输出结果 + 调用汇总
```

### 2.3 评审的最小流程

即使是"帮我看看这个逻辑有没有问题"，也必须至少经过：

```text
Master Agent 路由（识别为 PRD 评审）
    ↓
Review Agent 承接
    ↓
读取需求文档
    ↓
多维度检查
    ↓
输出评审报告 + 调用汇总
```

## 三、例外情况

以下情况可以简化流程，但仍需经过路由：

| 情况 | 简化方式 | 仍必须做的事 |
|------|----------|-------------|
| 用户明确说"直接执行，不用确认" | 跳过确认步骤 | 仍然路由、仍然经过 Agent |
| 用户说"不用评审，直接改" | 跳过 Review Agent | 仍然经过 Product Agent 和 Frontend Agent |
| 纯概念解释（"什么是状态机"） | General Agent 直接回答 | 仍然展示路由状态 |
| 用户要求停止当前工作流 | 停止执行 | 仍然输出当前状态 |

## 四、违规检测与恢复

### 4.1 自我检测

每个 Agent 和 Skill 在执行过程中应自我检测：

1. 我是否经过了正确的路由？
2. 我是否在正确的 Agent 职责范围内？
3. 我是否跳过了必要的步骤？
4. 我是否做了不属于我职责的事？

### 4.2 违规恢复

如果发现违规：

1. 立即停止当前操作
2. 说明违规内容
3. 返回 Master Agent 重新路由
4. 从正确的入口重新开始

---

## 五、用户豁免

用户可以在任何时候通过以下方式豁免部分约束：

| 用户指令 | 豁免内容 |
|----------|----------|
| "直接改，不用确认" | 跳过确认步骤 |
| "不用评审" | 跳过 Review Agent |
| "直接执行" | 跳过修改计划确认 |
| "不用走完整流程" | 简化流程（但仍需路由） |

**即使豁免，以下底线不可突破**：
- 必须经过 Master Agent 路由
- 必须展示路由状态
- 必须输出调用汇总
- 不能越过 Agent 直接修改
