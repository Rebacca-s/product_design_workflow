# 工作流 01：从模糊需求到完整交付物

## 概述

本工作流定义了一套完整的产品设计链路，从最模糊的需求描述出发，经过 8 个步骤，产出研发可直接使用的完整交付物包。

## 核心变化（v3.0 — 动态装配版）

| 对比维度 | v2.0（固定 12 章节） | v3.0（动态装配） |
|----------|---------------------|-----------------|
| PRD 结构 | 固定 12 章 | 25 章章节库，按需装配 |
| AI 章节 | 非 AI 写"不适用" | 非 AI 不生成 |
| 小迭代 | 同样结构 | 合并简化 |
| 章节新增 | 改流程 | 三步登记 |
| 交付物 | 固定 7 件 | 动态 4-7 件 |
| 规划文档 | 无 | 必须先生成 00_规划 |

## 适用条件

- 输入：一句或一段模糊的产品需求描述
- 输出：动态装配的完整交付物包
- 触发方式：`/product-start 需求描述`

## 依赖规则文件

执行本工作流时，必须遵循以下规则文件：

| 规则文件 | 用途 | 读取时机 |
|----------|------|----------|
| `rules/需求类型识别规则.md` | 识别需求类型 | Step 1 |
| `rules/交付物启用规则.md` | 决定启用哪些交付物 | Step 2 |
| `rules/PRD章节启用规则.md` | 决定启用哪些 PRD 章节 | Step 2 |
| `rules/PRD章节注册表.md` | 25 章章节库 | Step 4 |
| `rules/PRD章节外拆规则.md` | 判断章节是否外拆 | Step 5 |
| `rules/PRD章节增删规则.md` | 章节增删改规则 | 章节变更时 |
| `rules/研发交付标准.md` | 研发侧验收标准 | Step 8 |

## 工作流步骤

### Step 1：接收模糊需求 + 识别需求类型

**目标**：保留原始需求，识别需求类型。

**输出**：在对话中输出，不写文件。

```markdown
## 一、需求接收与类型识别

### 原始需求
[保留用户原始需求文本]

### 需求拆解

| 维度 | 判断 | 确定性 |
|------|------|--------|
| 产品类型 | App / 小程序 / Web / 后台 / 多端 | 确定 / 待确认 |
| 目标用户 | [画像] | 确定 / 待确认 |
| 核心场景 | [描述] | 确定 / 待确认 |
| 业务目标 | [描述] | 确定 / 待确认 |
| AI 产品 | 是 / 否 / 部分 | 确定 / 待确认 |
| 需要后台 | 是 / 否 | 确定 / 待确认 |
| 终端形态 | [形态] | 确定 / 待确认 |

### 需求类型识别

| 需求类型 | 是否命中 | 判断依据 |
|----------|----------|----------|
| 新产品需求 | 是/否 | [依据] |
| 大功能需求 | 是/否 | [依据] |
| 小迭代需求 | 是/否 | [依据] |
| AI 功能需求 | 是/否 | [依据] |
| 非 AI 功能需求 | 是/否 | [依据] |
| 后台管理功能需求 | 是/否 | [依据] |
```

**规则**：
- 根据 `rules/需求类型识别规则.md` 进行识别

- 如果超过 3 个维度不确定，先问不超过 5 个关键问题

### Step 2：生成交付物与章节规划

**目标**：先生成 `00_交付物与章节规划.md`，再按规划执行。

**输出文件**：`outputs/需求名称/00_交付物与章节规划.md`

**输出结构**：

```markdown
# 交付物与章节规划 — [需求名称]

## 1. 原始需求
[保留用户原始需求文本]

## 2. 需求类型判断
[需求类型识别结果表格]
```

**规则**：
- 根据 `rules/交付物启用规则.md` 决定交付物
- 根据 `rules/PRD章节启用规则.md` 决定章节
- 每个启用/不启用都必须写原因
- 小迭代需求标记"简化"

---

### Step 3：按规划生成交付物（除 PRD 外）

**目标**：根据 00 规划，生成 BRD 和需求分析。

**规则**：
- 如果 01_BRD 启用 → 生成 `01_BRD_业务需求说明.md`
- 如果 02_需求分析启用 → 生成 `02_需求分析与范围定义.md`
- 使用对应的模板文件

---

### Step 4：动态生成 PRD

**目标**：根据章节启用规划，生成 PRD 主文档。

**输出文件**：`outputs/需求名称/03_PRD_产品需求文档.md`

**执行规则**：

1. 读取 `rules/PRD章节注册表.md`，获取所有启用章节的登记信息
2. 按顺序生成每个启用章节：
   - 先读取注册表中该章节的"生成前读取"
   - 再读取对应方法论和模板
   - 生成章节内容
3. **不生成未启用的章节**（非 AI 需求不写"不适用"占位）
4. **小迭代需求合并简化** A 类章节
5. **信息不足时**写"待确认"和"当前假设"

---

### Step 5：判断章节是否外拆

**同 v2.0**，根据 `rules/PRD章节外拆规则.md` 的 10 条条件判断。

外拆后：
- 专项文档放入 `04_PRD_专项文档/`
- 命名格式：`章节ID_章节名称_专项说明.md`
- 主 PRD 保留：结论 + 核心规则 + 研发关注要点 + 专项文档路径

---

### Step 6：生成原型说明文档

**如启用**，生成 `05_原型说明文档.md`。

使用 `templates/原型说明模板.md`。

---

### Step 7：生成 HTML 原型提示词

**如启用**，生成 `06_HTML原型生成提示词.md`。

---

### Step 8：生成研发交付检查清单

**每次必须生成** `07_研发交付检查清单.md`。

**检查项动态生成规则**：
- 只检查本次启用的交付物
- 只检查本次启用的 PRD 章节
- 使用 `templates/研发交付检查清单模板.md`

---

## 输出目录结构

```text
outputs/需求名称/
├── 00_交付物与章节规划.md          ← 新增（每次必须）
├── 01_BRD_业务需求说明.md           （条件启用）
├── 02_需求分析与范围定义.md         （条件启用）
├── 03_PRD_产品需求文档.md           （每次必须）
├── 04_PRD_专项文档/                 （有外拆时）
│   ├── C2_模型选型_专项说明.md
│   └── ...
├── 05_原型说明文档.md              （条件启用）
├── 06_HTML原型生成提示词.md        （条件启用）
└── 07_研发交付检查清单.md          （每次必须）
```

## 知识沉淀

每次执行完完整工作流后，主动检查是否有可沉淀的内容：

- 新的方法论 → `knowledge/`
- 新的模板字段 → `templates/`
- 优秀的案例片段 → `examples/`
- 工作流步骤优化 → 更新本文件
- 规则优化 → 更新 `rules/`
- 章节增删 → 按 `rules/PRD章节增删规则.md` 操作
