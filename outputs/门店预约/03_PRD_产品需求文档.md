# PRD 产品需求文档 — 多爱宠门店预约

> 本文档是研发交付的总装文档。复杂内容的详细信息请参见 `04_PRD_专项文档/` 目录下的专项文档。

---

## A1. 需求背景

多爱宠小程序目前已支持商品购买和体检服务购买，但履约方式较为单一：商品只能寄货配送，体检服务虽有线下合作医院但缺少系统化的门店管理和核销闭环。

随着合作门店（自营门店、宠物医院、第三方体检医院）数量增长，需要建立统一的 O2O 履约体系，让用户可以在线选择门店、预约时间、到店核销，让门店可以自助管理可售范围和营业时间，让平台可以规模化管理和监控门店运营。

用户需求文档中已明确：本期核心不是让门店自由卖货，而是让平台已有的商品和体检服务支持门店自提和线下预约履约。

## A2. 需求目标

1. **履约方式扩展**：商品支持"线上寄货"和"门店自提"两种履约方式；体检服务支持"线上寄样体检"和"线下门店预约"两种履约方式。
2. **门店发现**：用户可通过门店列表发现附近门店，通过门店详情了解门店支持的商品和服务、查看门店评价。
3. **双入口下单**：用户既可从商品/体检入口选择门店，也可从门店入口选择商品/服务后下单。
4. **核销闭环**：支付成功后生成核销码（二维码+数字码），门店扫码/输入核销码完成核销，订单状态自动流转。
5. **门店自助管理**：门店后台支持营业时间维护、预约时间配置、商品/服务上下架、体检报告上传。
6. **评价体系**：核销后用户可评价门店，评价展示在门店详情页，为后续用户选择门店提供参考。

## A3. 用户角色与使用场景

## A5. 功能说明

### 核心结论

本次涉及小程序C端、平台总后台、门店后台三端共计 22 个功能点的详细说明，每个功能包含功能描述、用户操作、系统响应、交互规则。详细内容外拆至专项文档。

### 核心规则

1. 商品/体检服务的履约方式在详情页选择，不同履约方式后续页面展示不同内容
2. 门店只能在平台配置的可售范围内管理上下架，不能新增平台外的商品/服务
3. 核销码为静态码，支付成功后生成，订单详情页展示
4. 门店只能核销绑定到本门店的订单，跨门店不能核销
5. 评价以门店为单位，不按单体检项目拆分

### 研发关注要点

- 三端需保持数据一致性（平台配置→门店可售→小程序展示）
- 核销操作需做防重复提交处理
- 履约方式切换时需清空之前的选择（地址↔门店）

## A6. 页面与交互说明

### 核心结论

本次新增/改造页面涉及小程序端 6 个页面、平台总后台 4 个模块页、门店后台 5 个模块页。详细页面清单、跳转关系、每页设计说明外拆至专项文档。

### 核心规则

1. 小程序以移动端优先，后台以PC端为主
2. 门店列表默认按距离排序（需用户授权定位），平台可通过排序权重干预排序结果

- 门店选择器需要在商品详情页/体检详情页/订单确认页多处复用
- 核销确认页需在核销前展示订单关键信息供门店确认

## A7. 字段与规则说明

### 核心结论

本次新增门店、门店商品关联、门店服务关联、预约时间、核销记录、评价等核心数据实体，字段总量超 30 个。详细字段定义、校验规则、接口关键字段外拆至专项文档。

### 核心规则

1. 门店类型枚举：自营门店、合作宠物医院、第三方体检医院
2. 门店状态枚举：营业中、休息中、暂停预约、已关闭
3. 履约方式枚举：线上寄货、门店自提、线上寄样体检、线下门店预约
4. 商品订单状态：快递(待付款→待发货→待收货→待评价→已完成) + 自提(待付款→待使用→待评价→已完成)；体检订单：寄样(简化为5个状态) + 到店(待付款→待使用→检验中→待评价→已完成)；支持改期不限次
5. 评价评分范围 1-5 星，评价内容支持文字+图片

### 研发关注要点

- 门店商品配置表是平台商品池和门店的多对多关系
- 核销记录需关联订单、门店、核销人、核销时间
- 订单表需扩展：新增履约方式字段、门店ID字段、预约时间字段、核销码字段

## A8. 异常情况

| 异常场景 | 触发条件 | 处理方式 | 用户提示 |
|----------|----------|----------|----------|
| 定位未授权 | 用户拒绝位置授权 | 门店列表不按距离排序，改为按默认排序；展示"开启定位可查看附近门店"引导 | "开启定位后可按距离查看附近门店" |
| 门店已暂停预约 | 用户选择门店时门店状态变为暂停 | 门店选择器中该门店置灰，标注"暂停预约" | "该门店当前暂停预约，请选择其他门店" |
| 预约时段已满 | 用户选择的时段预约名额用完 | 时段置灰不可选 | "该时段已约满，请选择其他时段" |
| 支付超时 | 用户在支付环节超时未完成 | 订单取消，释放预约名额 | "支付超时，订单已取消" |
| 核销码无效 | 门店扫码后码不存在或已核销 | 门店后台提示无效原因 | "核销码无效：该订单已核销/不存在" |
| 跨门店核销 | 门店尝试核销非本门店订单 | 拒绝核销 | "该订单不属于本门店，无法核销" |
| 重复核销 | 对已核销订单再次核销 | 拒绝核销，提示已核销 | "该订单已于 X月X日 XX:XX 核销" |
| 体检报告上传失败 | 文件过大或网络异常 | 提示重试，保留表单数据 | "上传失败，请重试" |
| 商品已下架 | 用户下单时商品被门店下架 | 阻止下单 | "该商品在当前门店已下架" |
| 门店被平台关闭 | 用户已选门店被平台关闭 | 订单可正常核销（已下单不受影响），但新下单不可选该门店 | 门店选择器中不展示该门店 |
| 网络异常 | 核销时门店后台网络断开 | 提示网络异常，建议切换数字码手动输入 | "网络异常，请尝试手动输入核销码" |

## A9. 验收标准

- [ ] 商品详情页可选择"线上寄货"或"门店自提"，切换后后续流程正确
- [ ] 体检详情页可选择"线上寄样体检"或"线下门店预约"，选择线下时需选门店+时间
- [ ] 门店列表展示附近门店，包含名称、类型、地址、距离、营业时间、评分、状态
- [ ] 门店详情展示门店信息、可售商品列表、可预约服务列表、评价列表
- [ ] 商品门店自提订单确认页展示门店信息、提货说明，不展示收货地址
- [ ] 体检线下预约订单确认页展示门店信息、预约时间、到店须知
- [ ] 支付成功后订单详情展示核销码（二维码+数字码）
- [ ] 门店后台可扫码或输入核销码完成核销，核销前展示确认信息
- [ ] 已核销订单不可重复核销，非本门店订单不可核销
- [ ] 平台后台可新增/编辑/停用门店，可为门店配置可售商品和可预约服务
- [ ] 门店后台可维护营业时间和可预约时段
- [ ] 门店后台可对本门店商品/服务进行上下架
- [ ] 核销后用户可评价门店（评分+文字+图片），评价展示在门店详情页
- [ ] 门店后台可对已核销体检订单上传报告，用户在小程序可查看

## B1. 业务流程图

### 核心结论

本次涉及两大核心业务流程（从商品入口下单、从门店入口下单）和门店核销子流程，流程涉及C端用户、门店人员、平台运营三方。详细流程图外拆至专项文档。

### 核心规则

1. 两条购买路径（商品入口和门店入口）最终汇聚到同一个订单确认→支付→核销流程
2. 核销是线下履约的关键节点，触发订单状态变更和后续评价/报告上传
3. 商品自提核销后订单直接完成；体检预约核销后需等待报告上传

### 研发关注要点

- 核销操作需支持两种输入方式（扫码和手动输入数字码）
- 核销确认页必须在核销生效前展示，不可跳过

## B3. 状态流转

### 核心结论

商品订单和体检订单各自有快递/寄样 + 门店到店两条链路，在列表Tab中合并展示（如"待发货/待使用"同一Tab）。体检订单简化去掉3个冗余状态（已寄出取样器、已寄出样本、已收货待检验）。新增"待使用""待评价"和"已过期"状态。改期不限次数。

### 核心规则

1. 商品快递：待付款 → 待发货 → 待收货 → 待评价 → 已完成
2. 商品自提：待付款 → 待使用 → 待评价 → 已完成
3. 体检寄样：待付款 → 待寄出取样器 → 待寄出样本 → 检验中 → 待评价 → 已完成
4. 体检到店：待付款 → 待使用 → 检验中 → 待评价 → 已完成
5. "待使用"状态过期未到店 → 已过期（不退款、不释放名额，展示在"已完成"Tab）
6. 改期不限次数，截止预约日之前
7. 退款流程独立，保持现有状态（待处理→处理中→退款中→已完成/已拒绝/已取消）

### 研发关注要点

- 列表Tab合并规则见专项文档
- "待使用"过期由系统定时任务触发
- 退款状态保持现有体系不变，不与门店履约状态混用

## B4. 权限设计

### 核心结论

本次涉及三种角色：C端用户（小程序）、平台运营（平台总后台）、门店人员（门店后台）。不同角色在各自端口内拥有不同操作权限。详细权限矩阵外拆至专项文档。

### 核心规则

1. C端用户：查看门店、下单、查看自己的订单和核销码、评价门店、查看报告
2. 平台运营：管理所有门店、配置商品/服务、查看核销记录和评价（全局权限）
3. 门店人员：仅管理本门店（信息维护、上下架、核销、上传报告），不可跨门店操作

### 研发关注要点

- 门店后台登录需校验账号与门店的绑定关系
- 门店后台所有数据操作需限制在本门店范围内
- 平台运营不能核销订单（核销是门店操作）

## B6. 风险与依赖

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 门店后台推广难 | 合作门店不愿使用新后台 | 中 | 核销功能设计极简，降低学习成本；支持扫码核销降低门槛 |
| 用户不愿授权定位 | 门店列表无法按距离排序 | 中 | 提供默认排序（评分/评价数），引导开启定位 |
| 核销码静态码安全性 | 恶意截图冒用 | 低 | 订单详情展示用户信息，门店核销时需人工核对用户身份 |
| 门店网络环境差 | 扫码核销失败 | 中 | 同时支持数字码手动输入，核销功能做离线兼容 |
| 第三方体检医院数据对接 | 体检报告格式不统一 | 低 | 本期报告为手动上传文件（PDF/图片），不要求结构化数据 |
| 现有订单系统改造范围大 | 订单表扩展影响已有功能 | 中 | 新增字段设默认值，已有订单不受影响；充分回归测试 |

**关键依赖**：

| 依赖项 | 说明 | 责任方 |
|--------|------|--------|
| 现有商品/服务数据 | 平台已有商品池和体检服务池 | 后端 |
| 用户定位能力 | 小程序获取用户位置 | 前端 |
| 核销码生成服务 | 需开发二维码+数字码生成 | 后端 |
| 门店后台账号体系 | 需新建门店账号并与门店绑定 | 后端+平台后台 |
| 现有支付系统 | 支付流程不变 | 后端 |
